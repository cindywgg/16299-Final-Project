# Terrain Surveyor Snake Robot Simulation

**Project:** Terrain Surveyor Snake Robot Simulation  
**Platform:** MuJoCo & Python  
**Core comparison:** Fixed Gait vs. Terrain-Adaptive Gait

---

## Abstract

This final project implements a simplified terrain surveyor snake robot simulator in MuJoCo. The model is based on a previously developed serial snake robot in which the body is approximated as a chain of cuboid links connected by revolute joints. The original design was useful as a proof of concept for lateral undulation, but it was open-loop: the robot did not know what terrain it was on and did not adjust its gait when conditions changed. This concept was converted into a working MuJoCo simulator. The final simulator keeps the same mechanical abstraction but implements a control and environment layer. The robot moves through a sequence of terrain regions: normal terrain, low-friction terrain, high-friction terrain, rough terrain, and a slope-like difficult terrain region. The controller changes a small number of gait parameters, such as amplitude and frequency, based on the current terrain. The goal of this project was not to build a full biological snake model or reinforcement learning system, but to test whether simple terrain-aware gait adaptation improves movement compared to a fixed gait. The final experiment compares fixed and adaptive gaits using forward progress, lateral drift, measure of effort, and success rate. The fixed gait traveled farther overall, reaching 7.010 m compared to 6.380 m for the adaptive gait. However, the adaptive gait had a much lower final lateral drift of 0.002 m compared to 0.030 m. This suggests that the adaptive controller was more conservative and stable, while the fixed controller was faster. The result shows a clear tradeoff between speed and path stability.

## 1. Background and Motivation

The idea for this project was inspired by NASA’s Jet Propulsion Laboratory's EELS (Exobiology Extant Life Surveyor) system. EELs is a modular snake-like robot designed for extreme terrains and autonomy by autonomously using AI to balance task planning with motion. Its control system combines environmental sensing, feedback from physical contact, and autonomous decision-making to adjust motion and recover from failures on its own. Snake robots are useful because they can move through spaces that are difficult for wheeled or legged robots. A snake-like body can bend around obstacles, pass through narrow areas, and adapt its body shape to irregular ground. However, this also makes control difficult, as a gait that works on one surface may become inefficient or unstable on another.

The starting point for this project was an existing serial snake robot model made by Jerome Dinal Herath. This model made several simplifying assumptions: it treated snake motion as mostly planar, ignored scales, and approximated the body as a series of cuboids connected by revolute joints. Each joint rotated about the Z axis, which produced side-to-side bending in the plane. The original model used 21 cuboid links and 20 joints with limits of about ±25°. Its movement was generated by cycling groups of joints through discrete bending states such as `+2`, `+1`, `-1`, and `-2`. However, the limitation for this system was the controller. The original controller did not directly use a continuous sinusoidal equation. Instead, it split the body into four sections (head, body 1, body 2, and tail) and assigned each section one of several discrete bending states. Cycling those states created a traveling body shape. This demonstrated that simple rules can produce snake-like motion, but the controller had no feedback. It did not know where it was going, how fast it was moving, whether it was drifting, or whether the terrain changed. This project extends that idea by asking a more control-oriented question: Can a snake robot improve movement across changing terrain by adapting a small number of gait parameters?

## 2. Model and Simulator Implementation

The original model was written in SDF/Gazebo format. For this project, I converted it to MuJoCo because MuJoCo is easier to run from Python, easier to visualize, and better suited for collecting experiment metrics. The conversion preserved the structure of the original robot. Each SDF link became a MuJoCo body, each box collision/visual became a MuJoCo box geom, and each revolute joint became a hinge joint. The joint axis remained 0 0 1, matching the original Z-axis rotation. The ±25 degree joint limits were also preserved. The final MuJoCo model uses 21 cuboid body links and 20 actuated hinge joints. The first body has a free joint so the robot can translate and rotate on the ground. The remaining bodies are linked serially. This retains the simplified idea of the original robot while allowing the controller to be written directly in Python. The final simulator treats +Y as forward progress and X as lateral drift.

The environment is a shortened terrain course so that the robot can cross multiple terrain types within one run. The course contains:

| Color | Terrain | Forward-y region | Purpose |
|---|---|---:|---|
| Gray | Normal terrain | `y < 1.0` | baseline terrain |
| Blue | Low-friction terrain | `1.0 <= y < 2.0` | slippery surface |
| Green | High-friction terrain | `2.0 <= y < 3.0` | stronger traction |
| Brown | Rough terrain | `3.0 <= y < 4.0` | uneven ground |
| Tan | Slope-like terrain | `y >= 4.0` | difficult region |

The colored terrain regions are visual markers, while a large MuJoCo floor plane provides stable collision underneath. The rough terrain section includes small brown blocks as visual markers for bumps, but the main purpose of the rough section is to change the controller’s terrain label and gait behavior.

## 3. Controller and Methodology

The simulator supports two main control ideas. First, it preserves an original-style segmented controller using the `+2`, `+1`, `-1`, and `-2` bending states. This mode exists mainly to connect the MuJoCo simulator back to the original Gazebo model. The main experiment, however, uses a smoother sinusoidal traveling-wave controller:

```text
theta_i(t) = A sin(2*pi*f*t - i*phase_lag)
```

where

- `theta_i(t)` is the target angle for joint `i`,
- `A` is the amplitude and controls how much the robot bends,
- `f` is the frequency and controls how quickly the bending wave travels down the body,
- `phase_lag` shifts the wave down the body and controls the spacing of the wave across the joints.

The fixed controller uses the same gait parameters everywhere. The adaptive controller changes gait parameters depending on the terrain:

| Terrain | Amplitude | Frequency | Reason |
|---|---:|---:|---|
| Normal | `0.28` | `0.85` | baseline gait |
| Low friction | `0.24` | `0.95` | smaller bends to reduce slipping |
| High friction | `0.32` | `0.85` | stronger bending because traction is better |
| Rough | `0.31` | `0.75` | slower gait for stability |
| Slope-like | `0.33` | `0.70` | slower, larger-amplitude motion for difficult terrain |

The simulator smoots gait parameter transitions to reduce sudden effort spikes when the robot crosses from one terrain region into another. The simulator also uses a reduced-order propulsion term along +Y because a simple chain of cuboids on a flat plane does not naturally reproduce all of the anisotropic friction effects needed for realistic snake locomotion. This propulsion term represents the net forward ground reaction generated by lateral undulation. It is a modeling simplification, but allows the project to focus on gait adaptation rather than low-level contact tuning.

The main metrics for comparison are:

| Metric | Meaning |
|---|---|
| Forward distance | how far the robot moves along +Y |
| Average speed | forward distance divided by time |
| Lateral drift | absolute sideways X displacement |
| Measure of Effort | average difference between desired and actual joint angles |
| Success | whether the robot crosses the target distance |

Note that a higher effort value means the joints are lagging farther behind their target angles or the gait is harder to maintain.

The results from the final simulation run was:

| Controller | Forward distance (m) | Average speed (m/s) | Lateral drift (m) | Measure of Effort | Success |
|---|---:|---:|---:|---:|---:|
| Fixed gait | 7.010 | 0.078 | 0.030 | 0.058 | 1 (Success) |
| Adaptive gait | 6.380 | 0.071 | 0.002 | 0.059 | 1 (Success) |

---

## 4. Results, Analysis, and Conclusion

The final experiment shows that both controllers succeeded. The fixed gait traveled 7.010 m in 90 seconds, while the adaptive gait traveled 6.380 m. The fixed gait therefore moved farther and had a higher average speed, 0.078 m/s compared to 0.071 m/s. From a pure forward-distance perspective, the fixed gait performed better.

However, the adaptive gait had much lower final lateral drift. The fixed gait ended with 0.030 m of lateral drift, while the adaptive gait ended with only 0.002 m. This means the adaptive controller stayed closer to the intended centerline. The trajectory plot supports this interpretation. The fixed gait reaches a higher final Y position, but it has a wider lateral spread. The adaptive gait is more conservative and does not travel quite as far, but it tracks the path more tightly for much of the run.

The adaptive gait also changed its parameters correctly as it crossed terrain regions. The simulator log shows the robot moving from normal terrain into low-friction terrain, then high-friction terrain, rough terrain, and finally slope-like terrain. For example, on low-friction terrain the controller used lower amplitude and higher frequency. On rough and slope-like terrain, it used lower frequency and slightly larger amplitude. This confirms that the adaptive logic operated as intended.

There were also effort spikes at terrain transitions. For example, when the robot entered high-friction terrain, effort briefly rose to 0.201. When it entered the slope-like terrain, effort briefly rose to 0.321. These spikes make sense because the controller changes gait parameters at terrain boundaries, so the target joint positions shift and the actual joint positions temporarily lag behind. After those transitions, effort returns to a lower steady value.

The main conclusion is not that adaptive control always beats fixed control. Instead, the result shows a tradeoff. The fixed gait is faster and travels farther, but the adaptive gait is more stable in terms of final drift. This is technically reasonable as the adaptive controller intentionally slows down or modifies the gait on difficult terrain. Such movement improves caution and path tracking, but it can reduce total forward progress.

Several iterations were needed to make the simulator coherent. The first challenge was converting the original SDF/Gazebo model into MuJoCo. The basic link and joint structure transferred cleanly, but the controller had to be rewritten in Python. This ended up being useful because it made the gait parameters easier to change and made metric collection simpler. Another challenge was the terrain. Separate finite terrain boxes caused the robot to fall into empty space when it moved off the edge. The final version uses one large collision floor with colored terrain markers. This is less physically detailed, but it makes the simulation stable and allows the controller comparison to be measured reliably. The last challenge was the adaptive controller. The first adaptive controller was too conservative. It slowed down too much on low-friction, rough, and slope-like terrain, so the fixed gait traveled farther. I then made the adaptive gait less conservative and smoothed the parameter transitions between terrain regions. This reduced some effort spikes and made the adaptive behavior more coherent. However, the final results still show that the fixed gait travels farther overall, while the adaptive gait has lower final lateral drift. This means the adaptive controller worked, but did not outperform the fixed gait in every metric.

The final result is a working simulator, but there are clear improvements for future work. A better physical model would include anisotropic friction so the snake’s lateral wave naturally creates forward motion without a reduced-order propulsion term. The adaptive controller could also be tuned using optimization rather than manually selected parameters. Finally, per-terrain metrics could be used to identify exactly where the adaptive gait helps or hurts.

Overall, this project produced a working MuJoCo simulator for a Terrain Surveyor Snake Robot. It preserves the original idea of a serial cuboid-link snake but adds terrain regions, adaptive gait parameters, visualization, and quantitative evaluation. The final experiment showed that both fixed and adaptive controllers succeeded. The fixed gait moved farther and faster, while the adaptive gait had much lower lateral drift. This means the adaptive controller was more conservative but better centered. The result is technically meaningful because it shows the tradeoff between speed and stability in terrain-aware snake locomotion. The project also demonstrates the value of iteration. The simulator had to be corrected for coordinate direction, terrain stability, speed, and controller tuning. The final system is not a perfect biological snake model, but it is a coherent and measurable simulation that answers the main project question: simple terrain-aware gait adaptation can change locomotion behavior, but the chosen adaptation rules determine whether the benefit appears as speed, stability, or efficiency.
